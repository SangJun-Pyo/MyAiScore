# Scoring Rubric v0.3.1

정본 허브: [마스터 플랜](../00_MASTER_PLAN.md). 데이터 정본: [EVIDENCE_SCHEMA](EVIDENCE_SCHEMA.md). 교정 계획: [CALIBRATION_PLAN](CALIBRATION_PLAN.md).

## 1. 결정 상태와 평가 대상

5개 축·가중치·레벨 경계는 calibration_required인 교정 초안이다. 2026-09-10 Astra 검토를 반영해 **다섯 축 모두 판정 가능할 때만 종합점수를 발급**하는 구현 규칙을 채택했다. 이 규칙의 채택과 평가 타당성이 검증됐다는 주장은 별개다.

이번 프로젝트와 제출된 AI 협업 사례를 평가한다. 좋은 코드, 설정 파일 수, 토큰 사용량, 에이전트 수는 AI 활용 능력이나 개인 기여의 증명이 아니다. 단순한 도구도 문제에 맞게 선택하고 검증했다면 최고 레벨에 도달할 수 있다.

## 2. 평가 축과 가중치

| 코드 | 축 | 가중치 | 평가 질문 |
|---|---|---:|---|
| A | 문제 정의와 목표 부합 | 15 | 문제·제약·완료 조건을 정하고 목표 달성 여부를 확인했는가? |
| B | 맥락 제공과 위임 | 20 | 필요한 맥락과 작업 경계를 AI에 전달했는가? |
| C | 도구·접근 적합성 | 15 | 문제 규모에 맞는 방법을 선택하고 불필요한 복잡성을 피했는가? |
| D | 검증의 질 | 30 | AI 결과의 중요한 실패 가능성을 적절한 근거로 검증했는가? |
| E | 인간의 판단·수정·반복 | 20 | 제안을 근거로 채택·거절·수정하고 결과를 확인했는가? |

가중치 합계는 100이다. D를 가장 높게 둔 것은 제품 가설이며 실험 후 조정할 수 있다.

## 3. 미확인과 관찰된 낮은 수행의 구분

- observed: 해당 축의 행동과 근거가 연결돼 레벨을 판정할 수 있음. level은 정수 1~4.
- not_observed: 필요한 근거가 없음. level과 dimension_score는 null.
- insufficient_evidence: 근거는 있으나 너무 약하거나 관련성이 부족하거나 해결되지 않은 충돌이 있음. level과 dimension_score는 null.
- 관찰된 모든 판정은 최소 하나의 유효한 supporting_evidence_id와 판단 이유를 갖는다. 근거 개수 자체가 높은 레벨의 조건은 아니다.
- 검증 기록이 없다는 이유만으로 D=1로 판정하지 않는다. 검증을 생략한 행동이 과정 자료와 결과에서 확인됐을 때만 D=1의 근거가 될 수 있다. 사용자의 한 문장 자기진술만으로 사실을 확정하지 않는다.
- 파일 존재는 사용 여부나 실행 성공의 증거가 아니다. 코드와 모순되는 과정 주장도 코드만 보고 임의로 판정하지 않고, 판정에 필요한 충돌이 해결될 때까지 insufficient_evidence로 둔다.

## 4. 축별 레벨 기준 — 교정 초안

레벨 이름은 1 Emerging / 2 Directed / 3 Managed / 4 Exemplary다. 해당 축에서 근거가 지지하는 가장 높은 단계로 판정하되, 반례와 미확인 사항을 함께 기록한다. 다른 축의 강점으로 부족한 조건을 대신하지 않는다.

### A. 문제 정의와 목표 부합

| 레벨 | 관찰 가능한 행동 | 반례·경계 |
|---|---|---|
| 1 | 실제 요청은 있었지만 목적·완료 조건이 모호했고, 무엇을 해결했는지 확인하지 않은 행동이 드러남 | 요청 기록 자체가 없으면 not_observed |
| 2 | 목표나 입출력을 지정하고 정상 사례로 기본 완료 여부를 확인함 | README에 목표만 사후 작성한 것은 실제 사용 근거가 아님 |
| 3 | 제약·범위·완료 조건을 작업 지시에 연결하고 결과를 각 조건에 대조함 | 큰 기능 목록만 있고 충족 여부를 확인하지 않았으면 부족 |
| 4 | 핵심 가정을 검토해 필요하면 범위를 조정하고, 목표·제약에 맞는 성공과 실패 사례로 해결 여부를 확인함 | 복잡한 요구사항이나 긴 기획서 자체는 가산점이 아님 |

### B. 맥락 제공과 위임

| 레벨 | 관찰 가능한 행동 | 반례·경계 |
|---|---|---|
| 1 | 필요한 코드·제약을 누락한 채 위임하고 그로 인한 오해를 방치한 과정이 확인됨 | AGENTS.md가 없다는 사실만으로 낮은 레벨을 주지 않음 |
| 2 | 관련 파일이나 요구사항과 작업 범위를 전달하고 기본 오류를 보완함 | 저장소 전체를 무작정 제공한 것만으로 충분하다고 보지 않음 |
| 3 | 관련 맥락·인터페이스·완료 조건을 선별해 전달하고 피드백으로 맥락을 갱신함 | 단순 작업을 불필요하게 분해할 필요 없음 |
| 4 | 중요한 의존성과 맥락 누락을 사전에 관리하고 결과를 확인해 필요한 맥락만 보완함 | 에이전트 수나 프롬프트 길이는 단계 기준이 아님 |

### C. 도구·접근 적합성

| 레벨 | 관찰 가능한 행동 | 반례·경계 |
|---|---|---|
| 1 | 제약에 맞지 않는 도구나 과도한 구조를 선택했고 발생한 문제를 다루지 않은 과정이 확인됨 | 도구가 한 개이거나 무료라는 이유로 감점하지 않음 |
| 2 | 기본 도구가 문제에 맞고 핵심 작업을 수행했지만 한계·부담 검토는 제한적임 | 설정 파일 존재만으로 사용과 적합성을 판정하지 않음 |
| 3 | 속도·비용·유지보수·검증 가능성 중 관련 제약을 고려해 적절한 방법을 선택함 | 모든 도구를 실험하거나 비용 숫자를 반드시 기록할 필요 없음 |
| 4 | 관련 대안과 실제 결과를 근거로 최소한의 충분한 방법을 선택·조정하고 한계에 대응함 | 복잡한 오케스트레이션 자체나 사후의 멋진 설명만으로 최고 단계가 아님 |

### D. 검증의 질

| 레벨 | 관찰 가능한 행동 | 반례·경계 |
|---|---|---|
| 1 | AI 결과를 검증 없이 수용하거나 명백한 실패를 무시한 행동이 구체적 과정 자료로 확인됨 | 테스트·로그를 제출하지 않은 것만으로 검증 생략을 단정하지 않음 |
| 2 | 실행·수동 확인·리뷰 등으로 정상 사례를 확인했으나 주요 실패 조건은 놓침 | 테스트 파일만 있고 사용·결과 근거가 없으면 부족할 수 있음 |
| 3 | 중요한 실패 사례를 재현 가능한 테스트·리뷰·실측으로 확인하고 결과를 해석함 | 자동화 테스트가 필수는 아님. 작업에 적절한 재현 가능한 수동 검증도 인정 |
| 4 | 위험에 맞는 반례로 AI 결과를 반박해 보고, 변경 후 회귀와 남은 한계까지 확인함 | 테스트 수·커버리지 숫자·CI 파일 존재만으로 최고 단계가 아님 |

### E. 인간의 판단·수정·반복

| 레벨 | 관찰 가능한 행동 | 반례·경계 |
|---|---|---|
| 1 | 제안의 명백한 문제를 인식할 기회가 있었지만 근거 검토 없이 수용한 과정이 확인됨 | 수정 커밋이 없다는 이유만으로 무비판 수용으로 판정하지 않음 |
| 2 | 제안을 검토해 채택·수정·거절하고 간단한 이유를 제시함 | 근거 없이 “직접 판단했다”는 주장만으로 판정하지 않음 |
| 3 | 대안·제약·검증 결과에 따라 수용 여부를 결정하고 그 효과를 확인함 | 코드를 많이 수정하거나 AI 제안을 거절한 횟수는 가산점이 아님 |
| 4 | 실패 원인을 구분하고 위임·접근·검증 방식을 조정하거나, 충분한 근거로 그대로 채택하고 종료함 | AI 제안이 맞았다면 의도적인 거절·반복을 만들 필요 없음 |

## 5. 점수 공식과 발급 조건

입력은 5개 고유 코드 A~E의 CriterionResult, 유효한 Evidence 참조, ingestion_status다. 중복·누락 코드, observed인데 null인 레벨, 1~4 밖의 값, 끊긴 참조는 계약 오류로 거부한다. 이를 정상적인 점수 보류로 숨기지 않는다.

발급 조건:

1. ingestion_status가 complete. 계획된 샘플 수집의 완료를 뜻하며 저장소 전체 검증을 뜻하지 않는다.
2. A~E 다섯 축 모두 observed이고 지지 근거가 유효함.
3. 레벨 판정을 막는 미해결 충돌이 없음.

~~~text
dimension_score = level * 25
score = floor((sum(weight[code] * level[code] * 25) + 50) / 100)
~~~

가중치는 정수 15/20/15/30/20이며 위 정수식은 양수 half-up 반올림이다. 미확인 항목에는 공식을 적용하지 않고, 가중치 재분배도 하지 않는다.

발급 시 value는 정수 25~100이다. 최저 단계가 1이므로 현재 판정 체계에서는 0~24점이 발생하지 않는다. UI는 “100점 만점의 실험적 진단”이라고 설명하고 이 척도의 한계를 공개한다.

조건 미충족 시 my_ai_score.status=withheld, value=null이며 reasons에 insufficient_dimensions / ingestion_partial / unresolved_conflict 중 해당 사유를 기록한다. partial 수집은 항목 진단을 허용하지만 총점은 보류한다. 수집 자체가 failed이면 평가 상태 failed로 종료하며 채점 결과를 꾸며내지 않는다.

## 6. 계산·경계 예시 (모두 synthetic, 실제 평가 아님)

| 경우 | A/B/C/D/E | 결과 |
|---|---|---|
| 완전 관찰 | 3/4/3/2/3 | 72.5 → 73, issued |
| C 미확인 | 2/3/null/3/2 | withheld, value=null, observed_dimensions=4 |
| D 미확인 | 4/4/4/null/4 | withheld. 다른 축이 높아도 발급하지 않음 |
| E에 미해결 충돌 | 3/3/3/3/null | withheld, unresolved_conflict |
| 전부 최고, 수집 complete | 4/4/4/4/4 | 100 |
| 전부 최저 수행 관찰, 수집 complete | 1/1/1/1/1 | 25. 미관찰 사례와 다름 |
| 다섯 축 관찰, 수집 partial | 3/4/3/2/3 | withheld, ingestion_partial |

4/5 결과를 55점 등으로 발급하던 v0.3 초안은 폐기했다. 부분 근거를 숨겨도 점수를 얻도록 재정규화하지 않으며, 근거가 없다는 이유로 임의의 감점도 하지 않는다.

## 7. 표시와 재평가

보류여도 확인된 레벨·근거·미확인 사유·가장 중요한 다음 행동을 제공한다. “5개 항목 확인”은 개인 능력 인증이나 오류가 전혀 없다는 뜻이 아니다.

레벨 변화, 새로 제출된 근거, 실제 행동 변화는 서로 다르다. 비교 계약은 [EVIDENCE_SCHEMA](EVIDENCE_SCHEMA.md)의 Comparison을 따른다. 개인 기술 등급·Project Quality 총점은 MVP에서 제공하지 않는다.
