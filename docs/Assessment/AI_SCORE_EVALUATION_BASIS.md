# AI 활용 평가 점수 판단 근거

> 기준 시점: `main` 브랜치 `6c8b17c`  
> 현재 적용 규칙: `repository-report-v1` / `repository-signals-v1`

## 1. 핵심 요약

현재 사용자 화면에 표시되는 점수는 개인의 실제 AI 활용 능력을 직접 평가한 점수가 아니다. 공개 GitHub 저장소의 고정된 커밋에서 선택한 파일 표본을 대상으로, AI 협업에 도움이 될 수 있는 구조적 신호를 확인한 **저장소 기반 AI 협업 준비도**다.

현재 점수는 다음 방식으로 만들어진다.

1. 공개 GitHub 저장소의 파일 중 최대 40개를 선택해 읽는다.
2. 선택된 파일의 경로와 파일명이 14개의 고정 신호에 해당하는지 확인한다.
3. 발견된 신호마다 정해진 점수를 한 번씩 더한다.
4. 맥락, 검증 기반, 기록, 자동화의 네 축 점수를 합해 0~100점의 총점을 만든다.

```text
총점 = 맥락 + 검증 기반 + 기록 + 자동화
각 축 = 0~25점
총점 = 0~100점
```

LLM의 주관적 판정, 코드 품질, 파일 내용의 충실도, 테스트 성공 여부는 현재 점수에 반영되지 않는다.

구현 정본:

- 점수와 파생 결과: [`src/shared/repositoryReport.ts`](../../src/shared/repositoryReport.ts)
- 파일 신호 인식: [`src/server/repositoryReport/report.ts`](../../src/server/repositoryReport/report.ts)
- 파일 표본 선택: [`src/server/ingestion/fileSelection.ts`](../../src/server/ingestion/fileSelection.ts)
- 수집 제한: [`src/shared/contracts/ingestion.ts`](../../src/shared/contracts/ingestion.ts)

## 2. 현재 점수의 전체 판단 근거

### 2.1 맥락: 최대 25점

| 근거 | 점수 | 실제 인식 조건 |
|---|---:|---|
| 시작 안내 | 7 | 어느 경로든 파일명이 `README`, `README.md` 같은 형태 |
| AI·협업 지침 | 7 | 어느 경로든 `AGENTS.md`, `CLAUDE.md`, 또는 정확히 `.github/copilot-instructions.md` |
| 문서 공간 | 6 | 루트의 `doc/`, `docs/`, `documentation/` 아래에 있는 `.md`, `.mdx`, `.rst`, `.txt` 파일 |
| 프로젝트 설정 | 5 | 루트의 `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `pom.xml`, `build.gradle`, `composer.json`, `Gemfile` |

이 축은 함께 작업할 사람이 참고할 수 있는 맥락 구조가 저장소에 존재하는지를 나타낸다. 다음 항목은 확인하지 않는다.

- 문서 내용이 정확하거나 충분한지
- AI가 해당 지침을 실제로 따랐는지
- 현재 코드와 문서가 일치하는지
- 문서가 실제 작업 과정에서 사용됐는지

### 2.2 검증 기반: 최대 25점

| 근거 | 점수 | 실제 인식 조건 |
|---|---:|---|
| 테스트 흔적 | 21 | `test/`, `tests/`, `__tests__/` 경로 또는 `*.test.*`, `*.spec.*` 파일 |
| 검사 설정 | 4 | `tsconfig*.json`, ESLint, Vitest, Jest, Pytest, Tox, Ruff, Codecov, `.coveragerc` 설정 |

테스트 파일 하나가 발견돼도 21점이며, 같은 종류의 테스트 파일이 여러 개 발견돼도 21점이다. 다음 항목은 확인하지 않는다.

- 테스트가 실제로 실행됐는지
- 테스트가 통과하는지
- 테스트가 중요한 실패 조건을 다루는지
- 테스트 커버리지가 충분한지
- 검사 설정이 실제 명령이나 CI에서 사용되는지

### 2.3 기록: 최대 25점

| 근거 | 점수 | 실제 인식 조건 |
|---|---:|---|
| 변경 기록 | 8 | `CHANGELOG`, `CHANGES`, `HISTORY` 계열 파일 |
| 결정 기록 | 9 | `ADR`, `ADRS`, `decision`, `decisions` 경로·파일 또는 `ADR-0001`과 같은 이름 |
| 이슈·PR 틀 | 5 | `.github/issue_template/` 또는 `.github/pull_request_template...` |
| 변경 단계 | 3 | `migration/`, `migrations/`, `schema/migration/` 계열 경로 |

이 축은 변경과 결정을 다시 따라갈 수 있는 파일 구조가 존재하는지를 나타낸다. 기록의 사실성, 최신성, 작성자, 실제 의사결정과의 연결 여부는 확인하지 않는다.

### 2.4 자동화: 최대 25점

| 근거 | 점수 | 실제 인식 조건 |
|---|---:|---|
| 자동 검사 | 15 | `.github/workflows/` 아래의 `.yml` 또는 `.yaml` 파일 |
| 의존성 관리 | 4 | `dependabot.yml`, `dependabot.yaml` 또는 Renovate 설정 |
| 배포 준비 | 3 | `Dockerfile`, Compose, Railway, Vercel, Netlify, Fly, Render 설정 |
| 반복 작업 도구 | 3 | 루트 `script/`, `scripts/`, `tool/`, `tools/` 또는 `Makefile`, `Justfile`, `Taskfile` |

자동화 설정의 존재만 확인하며, 다음 항목은 확인하지 않는다.

- 워크플로가 최근 실행됐는지
- 워크플로가 성공했는지
- 배포 설정이 실제 운영에 사용되는지
- 자동화 명령이 안전하고 정확한지

## 3. 점수 계산의 공통 규칙

- 같은 근거 종류는 한 번만 계산한다.
- README나 테스트 파일이 여러 개 있어도 해당 신호의 점수는 한 번만 더한다.
- 각 축은 최대 25점으로 제한한다.
- 총점은 네 축 점수의 단순 합계다.
- 반올림, 백분율 환산, 별도의 가중평균은 사용하지 않는다.
- 근거 카드에는 각 신호에 해당하는 경로를 최대 5개만 표시한다.
- 실제 수집된 파일 경로에 없는 근거는 인정하지 않는다.
- 응답을 읽을 때 근거 카드에서 점수, 스타일, 부족 영역, 다음 도전을 다시 계산한다.
- 근거와 맞지 않게 점수 숫자만 변경된 응답은 거부한다.

현재 구현은 파일 내용을 점수 계산에 사용하지 않는다. 따라서 이름과 경로만 조건에 맞는 빈 파일도 정상적으로 수집되면 신호로 인정될 수 있다.

## 4. 스타일 판단 규칙

점수 외에 저장소의 네 축 분포를 바탕으로 스타일을 표시한다.

1. 총점이 20점 미만이면 `첫 신호 탐험가`
2. 네 축이 모두 10점 이상이고 최고점과 최저점의 차이가 6점 이하이면 `균형 잡힌 빌더`
3. 나머지는 가장 높은 축에 따라 다음 스타일을 사용한다.
   - 맥락: `맥락 지도 제작자`
   - 검증 기반: `검증 레이더`
   - 기록: `기록 수집가`
   - 자동화: `자동화 조련사`

최고점이 같은 축이 여러 개라면 다음 우선순위로 결정한다.

```text
맥락 → 검증 기반 → 기록 → 자동화
```

## 5. 부족 영역과 다음 도전

### 부족 영역

각 축의 점수가 10점 미만이면 해당 축을 부족 영역으로 표시한다. 수집 상태가 `partial`이면 표본 밖의 신호를 판단할 수 없다는 별도 안내를 추가한다.

### 다음 도전

가장 점수가 낮은 축에 해당하는 다음 도전을 하나 제안한다.

| 가장 낮은 축 | 다음 도전 |
|---|---|
| 맥락 | README나 작업 지침에 목표, 제약, 완료 기준 기록 |
| 검증 기반 | 중요한 동작을 깨뜨릴 수 있는 입력 하나를 테스트로 남기고 결과 확인 |
| 기록 | 선택 하나의 이유, 대안, 관련 파일을 결정 기록으로 남기기 |
| 자동화 | 반복 검사 명령 하나를 CI에 연결하고 실패 시 확인할 항목 기록 |

최저점 동점도 `맥락 → 검증 기반 → 기록 → 자동화` 순서로 선택한다.

## 6. 점수에 사용되는 파일 표본

저장소 전체가 아니라 수집 제한 안에서 선택된 파일 표본만 점수에 사용한다.

| 수집 제한 | 값 |
|---|---:|
| 탐색할 트리 엔트리 | 최대 2,000개 |
| 선택 파일 | 최대 40개 |
| 파일 하나의 크기 | 최대 60KB |
| 전체 수집 내용 | 최대 800KB |
| HTTP 요청 | 최대 48회 |
| 수집 시간 | 최대 45초 |
| 요청별 재시도 | 최대 1회 |

후보 파일이 40개 이하라면 조건에 맞는 파일을 모두 선택한다. 40개를 초과하면 대략 다음 순서로 표본을 구성한다.

1. 명시적으로 지정된 관련 경로
2. 루트 설정 파일 최대 6개
3. AI 지침 파일 최대 4개
4. 소스 2개, 테스트 1개, 문서 1개, 기타 1개 순환
5. fixture, example, archive, artifact는 여유가 있을 때 후순위로 선택

현재 공개 웹 요청은 저장소 URL만 받으므로 일반 사용자가 관련 경로를 별도로 지정하는 흐름은 노출되어 있지 않다.

## 7. 수집에서 제외되는 파일

다음 경로와 파일은 점수 표본에서 제외된다.

- `node_modules`, `.next`, `dist`, `build`, `.git`, `vendor`
- `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lockb`
- 이미지, 폰트, 압축 파일, 동영상, PDF, 실행 파일, DB 등 바이너리 가능 파일
- 심볼릭 링크
- 서브모듈
- 60KB를 초과하는 파일
- `.env`, `.env.*`, `.pem`, `.key`, `id_rsa`와 같은 비밀 가능 파일

수집한 텍스트에서 비밀 패턴이 감지되면 원문을 그대로 사용하지 않고 마스킹한다.

## 8. `complete`와 `partial`의 의미

`complete`는 저장소 전체를 검증했다는 뜻이 아니다. 계획된 파일 표본을 정해진 제한 안에서 읽었다는 뜻이다.

다음과 같은 경우 수집 상태가 `partial`이 될 수 있다.

- GitHub의 트리 결과가 잘린 경우
- 자체 탐색 한도 2,000개를 초과한 경우
- 시간, 요청 수 또는 전체 용량 한도에 도달한 경우
- 선택한 파일을 가져오지 못한 경우
- 읽은 파일이 바이너리이거나 허용 크기를 초과한 경우

현재 저장소 리포트는 `partial`이어도 발견된 신호로 숫자 점수를 발급한다. 부분 수집이라는 이유로 점수를 직접 감점하거나 총점을 보류하지 않고, 별도의 부족 영역 안내만 추가한다.

## 9. 현재 점수로 판단할 수 없는 것

현재 점수만으로 다음을 판단하거나 인증할 수 없다.

- 개인이 AI를 잘 사용하는지
- 어떤 코드가 AI에 의해 작성됐는지
- 사람과 AI의 실제 기여 비율
- 코드 품질이나 설계 품질
- 테스트와 CI의 실행 성공 여부
- 문서와 ADR 내용의 사실성
- AI 지침을 실제로 준수했는지
- 생산성이 향상됐는지
- 저장소가 안전하거나 운영 가능한지
- 채용이나 개인 역량 등급에 적합한지

따라서 현재 점수의 정확한 해석은 다음과 같다.

> 선택된 공개 저장소 파일 표본에서, AI 협업 준비에 도움이 될 수 있는 구조적 파일 신호가 얼마나 발견됐는지를 나타내는 결정론적 체크리스트 점수다.

현재 제품 계약도 이 점수를 개인의 AI 활용 능력, 코드 품질 또는 실행 성공에 대한 평가가 아닌 재미용 점수로 설명한다. 자세한 제품 경계는 [`REPOSITORY_REPORT.md`](REPOSITORY_REPORT.md)를 참고한다.

## 10. 레거시 5축 AI 협업 평가

저장소에는 현재 공개 저장소 점수와 별도로, 실제 AI 협업 과정의 근거를 평가하려던 과거 5축 체계가 남아 있다. 이 체계는 현재 저장소 기반 점수와 혼합하면 안 된다.

| 코드 | 평가 축 | 가중치 | 핵심 질문 |
|---|---|---:|---|
| A | 문제 정의와 목표 부합 | 15% | 문제, 제약, 완료 조건을 정하고 목표 달성 여부를 확인했는가? |
| B | 맥락 제공과 위임 | 20% | 필요한 맥락과 작업 경계를 AI에 전달했는가? |
| C | 도구·접근 적합성 | 15% | 문제 규모에 맞는 방법을 선택하고 불필요한 복잡성을 피했는가? |
| D | 검증의 질 | 30% | AI 결과의 중요한 실패 가능성을 적절한 근거로 검증했는가? |
| E | 인간의 판단·수정·반복 | 20% | 제안을 근거로 채택, 거절, 수정하고 결과를 확인했는가? |

각 축을 1~4레벨로 판단한다.

| 레벨 | 이름 | 축 점수 |
|---:|---|---:|
| 1 | Emerging | 25 |
| 2 | Directed | 50 |
| 3 | Managed | 75 |
| 4 | Exemplary | 100 |

```text
축 점수 = 레벨 × 25
총점 = A~E 축 점수의 가중평균을 양수 half-up 방식으로 반올림
```

총점은 다음 조건을 모두 만족할 때만 발급한다.

1. 수집 상태가 `complete`다.
2. A~E 다섯 축이 모두 `observed`다.
3. 모든 관찰 결과에 유효한 지지 근거가 있다.
4. 레벨 판정을 막는 미해결 충돌이 없다.

조건을 만족하지 못하면 미확인 축을 0점으로 처리하지 않고 총점을 `withheld`로 보류한다. 보류 사유는 다음과 같다.

- `insufficient_dimensions`: 다섯 축을 모두 판단할 수 없음
- `ingestion_partial`: 수집이 부분적으로만 완료됨
- `unresolved_conflict`: 근거 사이의 충돌이 해결되지 않음

이 5축 체계는 현재 문서에서 `calibration_required`인 교정 초안으로 분류되며, 현재 기본 공개 저장소 리포트의 점수 기준이 아니다. 상세 기준은 [`SCORING_RUBRIC.md`](SCORING_RUBRIC.md), 계산 구현은 [`src/server/scoring/scoreCalculator.ts`](../../src/server/scoring/scoreCalculator.ts)를 참고한다.

## 11. 최종 정리

현재 서비스의 0~100점은 실제 AI 활용 과정을 관찰해 판단한 능력 점수가 아니다. 선택된 저장소 파일의 경로에서 다음 네 종류의 구조적 준비 신호를 확인한 결과다.

- 함께 작업할 맥락이 파일로 남아 있는가
- 테스트와 검사 설정이 존재하는가
- 변경과 결정 기록을 따라갈 구조가 있는가
- 반복 검사를 자동화할 구조가 있는가
