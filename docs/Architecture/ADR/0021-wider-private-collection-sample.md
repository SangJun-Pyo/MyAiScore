# ADR-0021 — 60개 수집 표본과 사용자 화면의 원시 개수 분리

- 상태: Accepted
- 기록일: 2026-09-19
- 결정 주체와 근거: 더 넓은 파일 수집과 원시 수집 개수 비노출에 대한 사용자 요청, [Issue #51](https://github.com/SangJun-Pyo/MyAiScore/issues/51)
- 기록 성격: 구현과 함께 기록
- 대체 관계: [ADR-0017](0017-content-aware-repository-scoring.md)의 40개 선택 예산을 v2.5에서 확장한다.

## 배경

v2.3에서 파일 신호를 23개로 세분화한 뒤에도 선택 한도는 40개였다. 신호 대표를 먼저 예약하면 일반 소스·테스트·문서 표본이 작아져 내용 실질과 구조 진단의 해상도가 제한된다. 반대로 후보·선택·읽기 개수는 구현 진단에는 유용하지만 결과 화면의 핵심 해석을 방해하고, 사용자가 점수 계수로 오해할 수 있다.

## 결정

새 분석은 `repository-signals-v2.5`를 발급하고 선택 파일 상한을 40개에서 60개로 늘린다. 최대 파일 크기 60KB와 전체 decoded content 800KB는 유지한다. 추가 blob 요청을 수용하도록 HTTP 요청 상한은 48회에서 68회, 시간 상한은 45초에서 60초로 조정한다. 60개 파일이 평균 12KB일 때 720KB로 전체 내용 예산 안에 들어가며, 더 큰 파일이 많으면 기존처럼 partial과 구체적인 skip reason을 남긴다.

고정 HEAD의 로컬 tree 323개 후보를 같은 선택기로 재생한 결과는 다음과 같다.

| 표본 | 소스 | 테스트 | 문서 | 기타 |
|---:|---:|---:|---:|---:|
| 40 | 12 | 6 | 11 | 11 |
| 60 | 20 | 10 | 15 | 15 |

즉 신호 대표를 유지하면서 소스 +8, 테스트 +4, 문서 +4를 추가로 읽는다. 이 수치는 현재 MyAiScore 저장소의 고정 tree 비교이며 모든 저장소의 개선을 보장하지 않는다.

API와 브라우저 저장 계약에는 검증 가능한 coverage 개수를 계속 보존하지만 기본 결과 헤더와 내 리포트 목록에서는 후보·선택·읽기 개수를 표시하지 않는다. 대신 complete/partial과 정적 분석 범위만 보여준다. 상세 경로와 partial 이유는 유지한다.

## 대안과 결과

- **40개 유지:** 비용은 낮지만 세분화된 신호 예약 뒤 일반 표본이 너무 작다.
- **100개 이상 확대:** 요청 시간과 GitHub rate limit, 800KB 내용 예산의 균형이 불명확하다.
- **coverage 개수를 응답에서 삭제:** strict parser와 진단·재현 가능성을 약화하므로 UI에서만 숨긴다.

같은 SHA라도 v2.4와 v2.5는 선택 정책이 다를 수 있으므로 rule version과 selection policy version을 함께 올린다.
