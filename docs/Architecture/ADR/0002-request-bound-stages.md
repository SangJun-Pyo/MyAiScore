# ADR-0002 — 요청 안에서 단계를 실행하고 오래된 완료를 차단한다

- 상태: Accepted
- 기록일: 2026-09-14 (Phase 4 사후 기록)
- 결정 주체: Astra, 기존 단계 실행 원칙의 웹 구현
- 기준: PR #6 / `db0edd7`; 대체 관계: 없음

## 배경

응답 뒤에도 작업이 계속된다고 가정하는 폴링 설계는 실행 주체가 없으면 작업을 유실한다. 재시도, 중복 클릭, 입력 변경, 삭제와 느린 외부 응답이 경합할 수 있다.

## 결정

수집·질문·판정 요청은 해당 단계의 완료를 기다린다. GET 폴링은 상태 조회만 한다. 실행 전에 attempt ID, 입력 revision과 만료 시각을 저장하고 같은 실행권의 완료만 반영한다. 삭제 후 도착한 결과도 버린다. Idempotency-Key는 소유자·요청·입력과 결합하며 같은 키의 다른 입력은 거부한다. 중단된 작업은 명시적인 재시도로 복구한다.

## 대안

- 응답 후 프로세스 메모리에서 계속 실행: 프로세스 수명과 완료를 보장하지 못한다.
- 영속 큐와 별도 worker: 더 강한 복구 구조지만 현재 MVP에 운영 요소를 추가한다. 필요성이 확인될 때 도입한다.
- 조회 요청이 실행도 재개: 조회와 부작용을 섞어 중복 실행을 추적하기 어려워 배제했다.

## 결과와 재검토 조건

중복·늦은 완료를 제어하지만 프로세스가 죽은 작업을 자동 완료시키지는 않는다. 배포 플랫폼의 요청 제한이 처리 시간보다 짧거나 자동 복구/긴 작업이 필요하면 큐와 worker를 재검토한다. 세부 wire 계약은 [API_DATA_CONTRACTS](../API_DATA_CONTRACTS.md)를 따른다.
